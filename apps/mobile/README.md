# MoryDeals mobile MVP

Expo / React Native shopping shell with three pages — Browse, Cart and Lists — that share one Mory AssistantDock. Products are captured from the in-app merchant browser or by pasting a product link into the dock, then shown as cards in Cart. Uses the shared UI theme, Mory animation, product card and dock navigation from `packages/ui`. There are no bottom tabs.

## Run locally

From the repository root, in separate terminals:

```sh
npm run infra:up
npm run api
npm run worker
npm run mobile:ios
```

The API uses port `3000`; loopback is enough for the simulator, while a physical phone needs the API bound to `0.0.0.0`. Expo uses port `8091`. The UI showcase remains on `8090`. `npm run mobile:web` opens the same mobile UI in a browser.

For a physical device, put `EXPO_PUBLIC_API_URL=http://YOUR_LAN_IP:3000/api` in `apps/mobile/.env` and start the API with `API_HOST=0.0.0.0 npm run api` on a trusted development network. Restart Expo after changing its environment. The default loopback API is local development only; this MVP has no accounts or public deployment authentication.

`API_PROXY_PROFILE=dataimpulse-ca-sticky` in the root `.env` selects the configured Canadian pool. `API_DIRECT_HOSTS=bestbuy.ca,www.bestbuy.ca` makes those exact hosts use direct egress; it does not match other subdomains or alter merchant admission. The app never receives proxy or LLM credentials.

### Development build on a physical iPhone

The app is named MoryCart (`com.morydeals.cart`, scheme `morycart`) so it can sit beside the older MoryDeals app (`com.morydeals.app`, scheme `morydeals`). Signing uses team `4NJ4K8S975`.

1. Connect the iPhone by USB, unlock it and enable Developer Mode.
2. Put `EXPO_PUBLIC_API_URL=http://YOUR_LAN_IP:3000/api` in `apps/mobile/.env` and start the API with `API_HOST=0.0.0.0 npm run api` (trusted network only; the API has no authentication).
3. Build and install once: `LANG=en_US.UTF-8 npm run ios:device -w @morydeals/mobile`. CocoaPods needs a UTF-8 locale. If Xcode reports that no provisioning profile exists, build once with `xcodebuild -workspace ios/MoryCart.xcworkspace -scheme MoryCart -configuration Debug -destination id=DEVICE_UDID -allowProvisioningUpdates -derivedDataPath ios/build build`, then install with `xcrun devicectl device install app --device DEVICE_UDID ios/build/Build/Products/Debug-iphoneos/MoryCart.app`.
4. Day to day: `npm run start:dev -w @morydeals/mobile` (Metro on 8092, since 8081 is often used by the older app) and open MoryCart on the phone; JavaScript changes reload without rebuilding. Rebuild only after adding native modules or changing `app.json`.

`ios/` is generated by `expo prebuild` and is not committed. `plugins/with-scene-lifecycle.js` moves startup to Expo's `EXExpoAppSceneDelegate` on every prebuild: iOS 27 terminates apps built with Xcode 27 that keep the window-based lifecycle, which the Expo SDK 57 template still uses. Remove the plugin once the Expo template adopts UIScene.

## Responsibilities

- `src/ShoppingScreen.tsx`: page composition, shared dock, clipboard, save-to-list sheet and merchant navigation.
- `src/use-products.ts`: request lifecycle, duplicate submit prevention, retry, locally saved products, capture messages and error state.
- `src/products-api.ts`: URL validation, API calls, response validation and bounded polling that tolerates brief outages.
- `src/use-local-state.ts`: AsyncStorage hydration and serialized writes; unreadable data is kept under `<key>.corrupt` and the app starts fresh.
- `src/merchants/`: merchant catalog, in-app WebView browser, page capture and cosmetic filtering.
- `src/cart/`, `src/lists/`: Cart cards and named lists.
- `packages/ui`: presentation and animation only.
- `apps/api`: URL submission and job-status HTTP endpoints.
- `apps/worker`: existing queue consumer, acquisition, parsing, audit and database writes.

`EXPO_PUBLIC_API_URL` must include the `/api` prefix (trailing slashes are ignored). `POST /api/products` accepts only `{ "url": "https://…" }` and returns `{ id, status: "pending" }`. `GET /api/products/:id` returns pending, failed with a user-facing message, or ready with one normalized product. The API chooses crawl context; mobile cannot override worker settings. Queue submission uses the API's BullMQ provider and shared `@morydeals/capture-contracts` protocol/deduplication options. The API does not import or start the worker.

The app registers once with `POST /api/anonymous-users` and keeps the token in the iOS keychain (`expo-secure-store`; AsyncStorage on web); every API call sends it as a bearer token, and an unknown token re-registers once. The cart lives on the server per device: the local list is only an offline cache shown until `GET /api/cart` loads, products saved before the server cart existed are uploaded once, and Cart's pull-to-refresh reloads it. Sign-in will later link this device user to an account.

Cards show real data only. The mini chart beside the merchant draws the cart's 90-day history (Keepa Buy Box for Amazon, plus our own captures) as a step line ending at today's price, green at the 90-day low and red after a drop; without history it shows a single point. Products and named lists are stored on this device with AsyncStorage and restored after restart. Conversation messages remain in memory across page changes; they reset after restart. There is no account sync.

## Shopping shell

Browse, Cart and Lists share one AssistantDock. Navigation sits inside the input row and collapses while composing. The controlled `DockNavigation` component lives in the UI package; mobile owns page selection and haptic callbacks. Tap or drag selects a destination. The dock keeps its folded, half and full positions.

Browse shows the available merchants; the AI dock is the single place for store intent and product-link input. Cart uses compact vertical cards in a responsive masonry layout; Lists supports creating lists and adding/removing captured products. Card actions open the source store or save to a list. General chat currently explains the supported URL capture flow; it does not claim to set alerts or query an AI service.

## Merchant browsing

The home screen loads `GET /api/merchants`. Selecting a merchant opens a full-page native `react-native-webview` without the chat dock: the page fills the screen and a floating Mory (`MoryFab` from `packages/ui`) opens a speed dial of Capture, Previous page (browser history; disabled at the first page), Reload page, original/clean webpage, Cart (keeps the store session for the way back) and Home (back to Browse); it keeps clear of the bottom safe area. Browse and Cart support pull-to-refresh (`PullToRefresh` / `useMinimumRefresh`, at least one second, repeated pulls ignored); Browse reloads the store list, Cart's pull is presentational until server price refresh exists. There is no app header or address bar. iOS keeps native back/forward gestures; Android hardware Back navigates history before exiting. Returning to Browse and opening the same store restores that mounted session, including its URL and scroll position. Capture reads the current rendered HTML and URL (including variant parameters) and posts `{ url, html, capturedAt }` to `POST /api/products/snapshots`; the app does not parse the page. The browser stays open so shopping can continue; a short notice confirms the page was sent, a spinner shows while it is processed, and the product appears in Cart through the existing queue polling/card flow. The worker validates and parses this snapshot (the only place it is parsed), archives it, and persists the result without requesting the merchant again. Pages without a store parser fall back to server-side Markdown/LLM parsing. Opened store instances remain mounted in memory, so selecting the same merchant resumes its page. Loading and failed pages cannot be captured. Capture failures appear in a dismissible banner and do not require reloading the page. The capture time is set by the app, not the page. A failed snapshot capture is not retried with the same HTML — capture the page again; a capture that only timed out or lost connection resumes polling the existing job. `Others` opens an arbitrary HTTP(S) store link when enabled by the backend.

Automatic visits: after a store page settles (about 1.2 s, including in-page navigation) the app uploads the slimmed page once per URL to `POST /api/pages`, skipping URLs that look like account, sign-in, cart, checkout, order or wishlist pages (`src/merchants/visit-filter.ts`). When the worker finds a product page, the low strip above the page (`PageStrip`, 44 pt) shows the product with an add-to-cart control; otherwise it shows the store's logo and name. Found products are kept in history and listed under Recently viewed on the Lists page; only an explicit add (the strip, Recently viewed, or Capture) puts a product in the cart.

Web preview opens stores externally and uses paste-to-capture because it cannot read cross-origin browser navigation. Ghostery applies bundled, domain-scoped Fanboy cosmetic rules; the shield toggles them without reload. This does not block network requests or record cookie consent. See `src/merchants/filtering/README.md` for attribution and scope.

Native browsing is supplied by [react-native-webview](https://docs.expo.dev/versions/latest/sdk/webview/). Cookies and browser credentials are not read through browser APIs. The uploaded DOM can contain personalized page content; it is stored as an audit artifact. Selected options must be evidenced by the URL or captured HTML; ambiguous selections remain `needs_review`.

## Snapshot storage

API and worker must share `CAPTURE_SNAPSHOT_DIRECTORY` (default `.local/capture-snapshots`). The API stages gzip JSON; BullMQ carries only a UUID and SHA-256 reference. The worker archives the raw HTML and its parser result, then removes the staging file after successful persistence or once the job has failed with no retries left. Do not expose this directory publicly. Every page is slimmed in the WebView before upload: styles, SVG drawings, inline data images and page code are removed, while JSON data, known store state scripts and all text and elements stay, and a leading comment records the removal (a SHEIN listing page went from 2.4 MB to 150 KB; on all archived captures parse results were identical and pages a third smaller). The archived HTML is therefore not a pixel-faithful copy of the page. Snapshots are limited to 2 MiB HTML and accepted within five minutes of capture.
